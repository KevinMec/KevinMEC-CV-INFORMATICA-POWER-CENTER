Integración y Transformación de Archivos Planos: File-to-DB, DB-to-File y File-to-File

Un análisis técnico detallado sobre cómo construir pipelines de ingesta y extracción de datos utilizando archivos planos (CSV, DAT, TXT). Abordaremos la configuración de metadatos delimitados y de ancho fijo, así como la gestión de directorios del servidor ETL para asegurar la interoperabilidad con sistemas externos legacy.

01

Acto 1: El Desafío de la Desconexión de Sistemas (Archivos Planos)

En arquitecturas empresariales del mundo real, no todos los sistemas se comunican mediante conexiones directas a bases de datos relacionales. A menudo, las dependencias de terceros, los sistemas legacy o las plataformas SaaS entregan o requieren datos en formatos de "Archivos Planos" (Flat Files) como .csv, .txt o .dat.

El requerimiento para este proyecto consistió en construir tres flujos de integración independientes que garantizaran el procesamiento masivo de datos sin conexiones ODBC directas en los extremos del pipeline:

Ingesta (File to DB)

Cargar registros de clientes (customers_ff.txt) provenientes de un FTP directamente hacia tablas normalizadas en Oracle SQL.

Extracción (DB to File)

Extraer reportes estructurados desde la base de datos hacia archivos .csv para su consumo por herramientas externas.

Transformación (File to File)

Leer un archivo de texto, limpiar el formato y reestructurarlo en un nuevo archivo de ancho fijo (Fixed-Width) sin tocar la base de datos.

Esta situación me llevó a plantear: ¿Cómo configuro las propiedades exactas de importación de metadatos delimitados frente a los de ancho fijo, y cómo gestiona Informatica las rutas lógicas del servidor para evitar fallos por archivos "no encontrados"?
02

Acto 2: Topología de Flujos de Archivos y Metadatos

A diferencia de las tablas relacionales que proporcionan metadatos autodescriptivos al importar (nombres de columnas y tipos de datos), los archivos planos requieren que el desarrollador defina explícitamente la estructura (si es delimitado por comas, pipes o tabulaciones, o si es posicional).

Arquitectura: Manejo de Archivos Planos 3 Topologías de Pipeline ETL
Punto crítico de diseño: En Informatica, la lectura/escritura de archivos no se rige por cadenas ODBC, sino por variables de sistema a nivel del servidor, concretamente $PMSourceFileDir y $PMTargetFileDir.
03

Acto 3: Ejecución Técnica Paso a Paso

1

Importación de Metadatos y Estructuras en Informatica Designer

El problema: PowerCenter no puede interpretar un archivo plano sin que definamos su tipo (Delimitado vs Ancho Fijo) y si contiene o no cabeceras.

Decisión técnica: Utilizar el menú Source Analyzer -> Import from File. Durante el Wizard, seleccionar "Delimited", indicar la coma (,) como separador y activar la casilla "Import field names from first line".

Resultado verificado: Se generó el Source Qualifier correcto permitiendo ajustar los tipos de datos a String y Number. Para el caso "DB to File", se realizó el procedimiento inverso en el Target Designer -> Create -> Flat File.

2

Construcción de Mappings y Formato de Salida

El problema: Los archivos extraídos desde la base de datos (DB-to-File) se generaban sin la primera fila de cabeceras, lo que invalidaba el archivo para los sistemas de destino.

Decisión técnica: Aunque el Mapping Designer enruta los datos directamente, el formato final del Target Flat File requiere configuración. Entré a las propiedades del Target Flat File en el Mapping Designer, seleccioné el botón Advanced y establecí Header Options = Output Field Names.

Resultado verificado: El archivo extraído incluyó exitosamente la primera fila con los nombres exactos de los puertos, validando la estructura del reporte.

Referencia Lógica [Min 16:45] Target Designer - File Properties

Configuración avanzada del archivo de salida: Cambio de separador de Coma a Pipe (|) y activación de la opción Output Field Names para incluir las cabeceras en el archivo plano.

3

Configuración Crítica de Sesiones y Directorios del Servidor

El problema: Informatica ejecuta sus flujos en el lado del servidor, no en la máquina local. Si la sesión no tiene la ruta exacta donde reside físicamente el archivo, arroja el clásico error FR_3000 Error opening file.

Decisión técnica: En el **Workflow Manager** $\rightarrow$ Propiedades de la Sesión $\rightarrow$ Pestaña Mapping. Para las fuentes Flat File, configuré el atributo Source file directory usando la variable global $PMSourceFileDir\ y definí explícitamente el Source file name (ej. customers_ff.txt). Para el destino hice lo análogo utilizando $PMTargetFileDir\.

Justificación técnica: El uso de variables de entorno ($PM...) garantiza que el código sea escalable y portable entre los entornos de Desarrollo, QA y Producción sin necesidad de reescribir rutas hardcodeadas en disco (ej. C:\Informatica\server\...).

4

Ejecución en Workflow Monitor y Confirmación de Transmisión

El problema: Tras ejecutar los tres flujos, era necesario validar que los datos leídos del archivo plano llegaran a Oracle (File-to-DB), y viceversa.

Decisión técnica: Monitorear las estadísticas de ejecución (Run Properties) en el Workflow Monitor para contrastar las métricas de Applied Rows frente a Affected Rows.

Resultado verificado: Todos los flujos marcaron estado SUCCEEDED. Los archivos físicos generados en $PMTargetFileDir fueron abiertos en NotePad++, confirmando que respetaban los delimitadores elegidos (comas/pipes) y contaban con los Output Field Names correctos.

04

Acto 4: Aprendizajes Clave de Arquitectura (Flat Files)

El dominio de la importación, exportación y manipulación de archivos planos es una competencia indispensable en cualquier arquitecto de datos, ya que no toda la información viaja por conexiones ODBC.

1. Diferencia estructural en Metadatos

Las tablas relacionales declaran automáticamente su estructura al ser importadas. Los archivos planos no; dependen completamente de que el desarrollador defina si el parseo será Delimited (dinámico por un carácter como coma o pipe) o Fixed-Width (rígido, donde la columna X abarca del byte 1 al 15).

2. Portabilidad de Variables Globales

Nunca se deben *hardcodear* rutas como C:\Users\Data\File.csv en el servidor. El uso sistemático de $PMSourceFileDir y $PMTargetFileDir asegura que los Workflows puedan migrar de servidores Windows a UNIX/Linux sin romper los jobs en Producción.

3. Precisión de Cadenas (Strings)

Al importar Flat Files, Informatica suele asignar una longitud por defecto (ej. 10 o 255 bytes). Es una mejor práctica analizar la longitud real de la fuente y aumentar generosamente la Precisión del Source Qualifier para prevenir truncamientos silentes en flujos productivos de datos sucios.
