Construcción y Optimización de un Pipeline ETL con Lookup Dinámico

Un recorrido técnico en primera persona sobre cómo abordé la integración de datos heterogéneos de cricket (IPL), resolví cuellos de botella en consultas relacionales, gestioné memorias caché en el servidor ETL y corregí errores de rutas en archivos planos.

01

Acto 1: El Diagnóstico Inicial y la Inconsistencia de Datos

Cuando comencé a analizar el conjunto de datos deportivos para este proyecto, me encontré con un problema clásico de ingeniería de datos: los registros estaban dispersos en tablas relacionales sin restricciones y los datos de referencia estaban incompletos.

Específicamente, los datos de los jugadores (PLAYERS) y el rendimiento en los partidos (MATCHES) existían en Oracle SQL, pero la tabla maestra de equipos (TEAM_INFO) no contenía información para el equipo Gujarat Titans (GT). Esto me forzó a diseñar una estrategia capaz de manejar registros huérfanos sin romper el flujo de carga.

Datos Faltantes

Falta intencional de registros de equipos en la tabla referencial para poner a prueba los escenarios de Not Found.

Búsquedas Ineficientes

La ausencia de claves primarias e índices obligaba al motor a realizar Full Table Scans costosos en cada cruce de información.

Fallos en Flat Files

Al integrar salarios en formato CSV, el motor de Informatica abortaba la sesión al buscar archivos en la ruta de fuentes y no en la de caché.

Esta situación me llevó a preguntarme: ¿Cómo puedo garantizar que las búsquedas sean eficientes a nivel de base de datos y que el pipeline clasifique de manera transparente los datos con o sin coincidencia?
02

Acto 2: Definición de la Solución y Diagrama de Flujo

Para resolver este desafío, decidí construir una solución de dos capas: primero, optimizar el esquema relacional en Oracle mediante indexación adecuada; segundo, diseñar un pipeline modular en Informatica PowerCenter utilizando un Connected Lookup con evaluación condicional de resultados.

Diagrama de Flujo de Datos ETL Oracle / CSV → PowerCenter → Target

Elegí utilizar un Connected Lookup en lugar de un Unconnected Lookup porque necesitaba retornar múltiples columnas de metadatos (TEAM_CITY y TEAM_COACH) para cada fila entrante en el flujo directo de datos.

Con el diseño trazado: El siguiente paso fue la implementación técnica paso a paso en Oracle e Informatica.
03

Acto 3: Ejecución Técnica Paso a Paso

1

Optimización del Esquema Relacional en Oracle SQL

El problema: Sin Primary Keys ni índices, las consultas de cruce en Oracle ejecutaban Full Table Scans innecesarios.

Decisión técnica: Agregar restricciones relacionales (PK / FK) e índices B-Tree específicos en las columnas de unión (TEAM_NAME, PLAYER_ID).

Resultado verificado: Se aceleró el tiempo de construcción del índice de caché en Informatica y se aseguró la eliminación en cascada.

-- ==========================================
-- 1. TABLA REFERENCIAL DE EQUIPOS (Lookup Table)
-- ==========================================
CREATE TABLE TEAM_INFO (
    TEAM_NAME VARCHAR2(100) NOT NULL,
    TEAM_CITY VARCHAR2(255) NOT NULL,
    TEAM_COACH VARCHAR2(255) NOT NULL,
    TEAM_FOUNDED_YEAR NUMBER(4),
    CONSTRAINT PK_TEAM_INFO PRIMARY KEY (TEAM_NAME)
);

-- Índice B-Tree explícito en la ciudad para acelerar búsquedas
CREATE INDEX IDX_TEAM_CITY ON TEAM_INFO(TEAM_CITY);

-- ==========================================
-- 2. TABLA MAESTRA DE JUGADORES (Source 1)
-- ==========================================
CREATE TABLE PLAYERS (
    PLAYER_ID NUMBER NOT NULL,
    PLAYER_NAME VARCHAR2(255) NOT NULL,
    TEAM_NAME VARCHAR2(100) NOT NULL,
    CONSTRAINT PK_PLAYERS PRIMARY KEY (PLAYER_ID)
);

-- Índice en la clave de unión relacional para acelerar la construcción de la caché
CREATE INDEX IDX_PLAYERS_TEAM ON PLAYERS(TEAM_NAME);

-- ==========================================
-- 3. TABLA DE RENDIMIENTO EN PARTIDOS (Source 2)
-- ==========================================
CREATE TABLE MATCHES (
    MATCH_ID NUMBER NOT NULL,
    PLAYER_ID NUMBER NOT NULL,
    MATCHES NUMBER DEFAULT 0 NOT NULL,
    RUNS NUMBER DEFAULT 0 NOT NULL,
    WICKETS NUMBER DEFAULT 0 NOT NULL,
    CONSTRAINT PK_MATCHES PRIMARY KEY (MATCH_ID),
    CONSTRAINT FK_MATCHES_PLAYERS FOREIGN KEY (PLAYER_ID) 
        REFERENCES PLAYERS(PLAYER_ID) ON DELETE CASCADE
);

-- Índice en la Clave Foránea para optimizar el Joiner (JNRTRANS) por PLAYER_ID
CREATE INDEX IDX_MATCHES_PLAYER_ID ON MATCHES(PLAYER_ID);

Configuración del Mapping en Informatica Designer

El problema: Se requería unificar estadísticas de partidos con datos demográficos y evaluar la validez del equipo en una sola pasada.

Decisión técnica: Interconectar una Joiner Transformation (JNRTRANS) con un Connected Lookup (LKPTRANS) y una Expression Transformation (EXPTRANS).

Resultado verificado: Se generó una lógica limpia donde la evaluación del valor nulo asigna explícitamente la categoría de búsqueda.

Lógica de Evaluación en EXPTRANS:
IIF(ISNULL(TEAM_CITY), 'Not Found', 'Found')

Si el puerto devuelto por el Lookup (TEAM_CITY) es nulo, se marca como 'Not Found'; de lo contrario, se asigna 'Found'.

4

Pruebas de Caché, Políticas de Duplicados y Depuración

El problema: Al probar comportamientos de caché estática vs dinámica e insertar filas duplicadas en la base de datos, la política de coincidencia múltiple predeterminada abortó la sesión por ambigüedad de claves.

Decisión técnica: Configurar la política de coincidencia múltiple (`First Value` / `Last Value` / `Report Error`) según el requerimiento de negocio y aplicar un script de depuración por ROWID antes de definir restricciones estrictas.

Resultado verificado: Se depuraron las filas duplicadas conservando el primer registro válido, permitiendo agregar la clave primaria y restaurar la ejecución continua.

Static Cache (Estática) Se carga 1 vez al iniciar la sesión. No captura cambios realizados en la BD relacional durante la ejecución.
Dynamic Cache (Dinámica) Se actualiza dinámicamente en memoria con cada fila entrante. Ideal para CDC y dimensiones SCD Tipo 2.
Script de Limpieza Relacional por ROWID y Asignación de PK: 
-- Eliminación de duplicados dejando únicamente el primer registro por ROWID
DELETE FROM TEAM_INFO T
WHERE ROWID NOT IN (
    SELECT MIN(ROWID)
    FROM TEAM_INFO
    GROUP BY TEAM_NAME
);

-- Asignación de restricción Primary Key para garantizar unicidad en la caché
ALTER TABLE TEAM_INFO ADD CONSTRAINT PK_TEAM_INFO PRIMARY KEY (TEAM_NAME);

COMMIT;

Integración de Archivos Planos (Flat Files) y Troubleshooting de Rutas

El problema: Al integrar el archivo salaries.csv mediante una Flat File Lookup, la sesión falló con el error FR_3000 Error opening lookup source file a pesar de existir en el directorio estándar de fuentes.

Decisión técnica: Comprender la arquitectura interna de Informatica Server: las transformaciones de búsqueda sobre archivos planos leen por defecto del directorio de cachés ($PMCacheDir o subdirectorio LKPFILES), no de $PMSourceFileDir.

Resultado verificado: Se reubicó físicamente salaries.csv a la carpeta de Lookup Files, se declaró la propiedad Lookup source file name = salaries.csv y el workflow finalizó con carga exitosa en TCT_CRICKET_PLAYERS.

Acto 4: Aprendizajes Clave y Conclusiones del Proyecto

Este caso de estudio práctico me permitió consolidar habilidades críticas en el diseño e implementación de procesos ETL de nivel profesional. Los tres aprendizajes más relevantes fueron:

1. Impacto de la Indexación

Definir claves primarias e índices B-Tree en la base de datos relacional reduce drásticamente el tiempo de construcción de archivos de caché en Informatica.

2. Manejo de Caché en Memoria

Entender las diferencias entre Static y Dynamic Cache es fundamental para elegir la estrategia adecuada en cargas incrementales o dimensiones SCD.

3. Arquitectura del Servidor

Diferenciar las rutas de trabajo del servidor ($PMSourceFileDir vs $PMCacheDir) evita errores de ejecución al trabajar con Flat Files.
